Plugin Architecture: Ports, Adapters, and the Substitution Contract

How to make one module replaceable by another without the rest of the system noticing — and why the interface is the easy half.

You want to write registry.resolve("data_source", "fmp") instead of EdgarClient(), and have everything downstream keep working. This lecture is about what has to be true for that to be safe.

The naive view is that this is an interface problem: define the methods, make both classes implement them, done. That view is wrong in a specific and expensive way, and most of this lecture is about the gap it leaves.

1.1 What this is actually called

"Pluggable" is the word everyone reaches for and nobody writes in a paper. It is serviceable in conversation, but it names a property rather than a mechanism, and if you use it in an interview you will sound like you learned this from a blog post. The concept decomposes into several established terms, each naming a different part of the machinery.

Which term to use, and when

Writing the spec: "ports and adapters" and "registry" — precise, and already your project's vocabulary.
Talking to an interviewer: "hexagonal architecture with a service-provider registry; dependency inversion at every domain boundary." Concrete and checkable.
Reading the literature: search variability management and variation point binding time. That is where the analysis of when a variant is bound — compile time, load time, run time — is worked out properly, and it is precisely the axis on which your Layer 3 and Layer 4 differ.

That last row is worth dwelling on, because it dissolves a question you already ran into. "Swap an implementation by config" and "the orchestrator picks a variant per ticker" are not two features — they are one variation point with two binding times: load time and run time. Naming it that way makes the relationship obvious and tells you they share a mechanism.

1.2 The interface is not the contract

An interface is a syntactic promise: these method names, these argument types, this return type. A contract is a semantic promise: what the method actually guarantees about the values it returns.

Barbara Liskov's substitution principle (1987) states the requirement precisely. If S is a subtype of T, then objects of type T may be replaced by objects of type S without altering the correctness of the program. Unpacked into rules a substitute must obey:

  • Preconditions may not be strengthened. The substitute cannot demand more of its caller than the original did.
  • Postconditions may not be weakened. The substitute must guarantee at least as much about its output.
  • Invariants must be preserved. Anything true of the type before must stay true.

A type checker verifies none of these. It verifies the signature. This is why "it type-checks" and "it is substitutable" are different claims.

The worked example from your own pipeline

Two adapters satisfy DataSourcePort: EdgarAdapter and FmpAdapter. Both return financial line items. Both type-check. But EDGAR's facts carry an explicit period start and end, so a discrete quarter can be distinguished from a cumulative year-to-date figure by arithmetic. FMP exposes only the period end, so it must guess — and on MU it guessed wrong by 71%.

That is a postcondition the port never wrote down. EdgarAdapter guarantees "the returned value is a discrete-period figure"; FmpAdapter guarantees "the returned value is probably a discrete-period figure." Weakened postcondition — an LSP violation hiding behind a satisfied type signature. The bug is not in either adapter. It is in the port, for failing to state the guarantee.

The lesson generalises: when you define a port, you are not choosing method names. You are deciding what every future implementation will be obliged to guarantee. Write the guarantees down, in the port's docstring, as testable statements.

1.3 Ports and adapters

The structural pattern is hexagonal architecture, also called ports and adapters. The rule is a dependency direction:

  • The port is an abstract declaration owned by the inside — your domain logic.
  • The adapter implements it and lives at the edge, where the vendor SDK, the HTTP call, or the file format lives.
  • Dependencies point inward. Domain code imports the port. It never imports the adapter.

The payoff is that your domain logic has no idea whether prices came from EDGAR, FMP, or a fixture file. That is what makes it testable, and it is the same property that makes it pluggable — testability and pluggability are the same property viewed from two angles.

1.4 Protocol or ABC?

Python gives you two mechanisms, and they differ in when and how conformance is decided.

 typing.Protocolabc.ABC

Default to Protocol. It keeps the port a pure declaration with no implementation, which means the port file imports nothing and can be depended on freely. Reach for ABC only when adapters genuinely share behaviour worth inheriting.

# src/shared/ports/prices.py — pure typing, zero implementation
from typing import Protocol, runtime_checkable
import pandas as pd

class PricePort(Protocol):
    """Daily price history for one symbol.

    CONTRACT — every implementation must guarantee:
      C1  index is a timezone-naive DatetimeIndex, sorted ascending, unique
      C2  no row has a date > as_of                  (no look-ahead, INV-1)
      C3  columns ⊇ {open, high, low, close, adj_close, volume}
      C4  close is never NaN; a gap is an ABSENT ROW, never a filled one
      C5  raises SymbolUnknown, never returns empty, for an unknown symbol
    """

    def history(self, symbol: str, start: pd.Timestamp,
                as_of: pd.Timestamp) -> pd.DataFrame: ...
Note the shape of C1–C5

Every one is a statement that can be turned mechanically into an assertion. That is the test of whether you have written a contract or merely a wish. "Returns clean data" is a wish. "close is never NaN; a gap is an absent row" is a contract.

Trap

@runtime_checkable makes isinstance(x, PricePort) legal, but it only checks that the method names exist. It does not check signatures, types, or anything semantic. An object with a history attribute set to None passes. Never use it as your validation gate.

1.5 The registry

A registry is a map from a key to a way of building an implementation. That is all it is. The design decisions are in the details.

# src/shared/registry/registry.py
from dataclasses import dataclass
from typing import Callable, Any

@dataclass(frozen=True)
class Key:
    port: str        # "price", "ranking_model", "agent.fundamental"
    variant: str     # "edgar", "lightgbm", "scorecard"

@dataclass(frozen=True)
class Entry:
    factory: Callable[..., Any]   # build it, don't BE it
    version: str                  # semver of the IMPLEMENTATION
    experimental: bool = False

class Registry:
    def __init__(self) -> None:
        self._entries: dict[Key, Entry] = {}

    def register(self, port, variant, factory, version, experimental=False):
        key = Key(port, variant)
        if key in self._entries:                # fail loud (P5)
            raise DuplicateRegistration(key)
        self._entries[key] = Entry(factory, version, experimental)

    def resolve(self, port, variant, **kwargs):
        try:
            entry = self._entries[Key(port, variant)]
        except KeyError:
            available = sorted(k.variant for k in self._entries if k.port == port)
            raise UnknownVariant(port, variant, available) from None
        return entry.factory(**kwargs)

    def validate_coverage(self, required: list[str]) -> None:
        """Called ONCE at startup. Turns a 3am KeyError into a boot failure."""
        missing = [p for p in required
                   if not any(k.port == p for k in self._entries)]
        if missing:
            raise IncompleteRegistry(missing)

Four decisions worth making deliberately

  • Store factories, not instances. Registering a live object forces construction at import time, couples registration order to configuration, and makes every consumer share mutable state.
  • Fail loudly on duplicate registration. Silent overwrite means the last import wins, and import order is not something you want load-bearing.
  • Put the available variants in the error. UnknownVariant("price", "fpm", ["edgar","fmp","fixture"]) diagnoses the typo. A bare KeyError does not.
  • Validate coverage at startup. This is the single highest-value line in the class — see below.
The registry's real cost: it is a Service Locator

Dependency injection makes a module's needs visible in its signature: def __init__(self, prices: PricePort). A registry hides them behind a lookup: registry.resolve("price", cfg.variant). You have traded a compile-time error for a runtime one, and made dependencies invisible to the reader.

Two mitigations, and you want both: (1) validate_coverage() at startup, so failures land at boot rather than mid-run; (2) resolve at the composition root only — one wiring module — and inject the resolved object downward. Domain code should receive a PricePort, never reach for the registry itself.

1.6 Contract tests: the technique that makes substitution safe

Here is the core idea of the lecture. You write one test suite against the port, and run it against every implementation. The suite is the executable form of C1–C5.

# tests/contracts/test_price_port.py
import pytest

# Every registered variant gets pulled in automatically. A new adapter
# that forgets to add itself here is the bug this parametrisation catches.
@pytest.fixture(params=["edgar", "fmp", "fixture"])
def port(request, registry):
    return registry.resolve("price", request.param)

def test_c2_no_lookahead(port):
    """C2 · INV-1 — no row may postdate as_of, for ANY implementation."""
    as_of = pd.Timestamp("2026-06-30")
    df = port.history("AAPL", pd.Timestamp("2026-01-01"), as_of)
    assert df.index.max() <= as_of

def test_c4_gaps_are_absent_not_filled(port):
    """C4 — a missing day is a missing ROW. A forward-filled close is a
    fabricated observation, and no downstream feature can detect it."""
    df = port.history("AAPL", pd.Timestamp("2026-01-01"), pd.Timestamp("2026-06-30"))
    assert df["close"].notna().all()

def test_c5_unknown_symbol_raises(port):
    """C5 · P5 — fail loud. An empty frame is indistinguishable from a
    real halt, and downstream will treat it as data."""
    with pytest.raises(SymbolUnknown):
        port.history("NOTATICKER", ...)
Why this matters more than the registry

The registry lets you swap implementations. The contract test is what makes the swap safe. Without it, "pluggable" means "the program still starts" — and the MU-71% class of bug ships silently, because the type signature was never the thing that was wrong.

It also has a pleasant side effect: it forces the contract to be honest. If FmpAdapter cannot pass test_c2, you have learned something true about your data source, and you learned it in CI rather than in a backtest six months later.

1.7 When not to build a port

Abstraction has a price: indirection, a second file to read, and a boundary that constrains future change. The discipline that keeps it worth paying is a rule your project already states as CA-5:

Create a port only where a second implementation actually exists, or is contractually promised.

A port with a single implementation is a guess about the future written in code. It is also the most common form of over-engineering in codebases that have just discovered hexagonal architecture. Two honest exceptions:

  • A real implementation plus a test double is genuinely two — the fixture adapter is not a fake requirement.
  • A boundary to a system you do not control (a vendor API) earns a port on risk grounds even at one implementation, because the second one arrives when the vendor changes, not when you choose.

Interactive Agents: Configuration Influence and Structured Argument

Two different mechanisms that get called "agents talking to each other" — with different failure modes, different tests, and only one of them non-deterministic.

You want two things. First: one agent's output should influence another's configuration — the fundamental analyst notices high volatility, so the quant model runs at a one-week horizon rather than one month. Second: two agents should be able to argue before concluding.

These sound like one feature. They are not, and conflating them is the most common design error in multi-agent systems.

 A · Configuration influenceB · Argumentation
What flowsA variant name — controlA claim — content
MechanismRouting functionMessage state machine
Determinismdeterministic, replayableLLM in the loop
Primary hazardCycles; loss of independenceSycophancy; correlated errors
Cost to testLow — it is a pure functionHigh — needs a measured study

Because their failure modes are disjoint, they belong in separate specs — F6a and F6b. Part A is cheap, deterministic and useful on its own. Part B is expensive and needs evidence before you believe it.

2.1 What an "agent" actually is

Strip the marketing. An agent is a component that (i) perceives some state, (ii) decides on an action, possibly using a model, (iii) acts through tools that change the world or gather more information, and (iv) carries state across steps.

An LLM call is not an agent. A function that calls an LLM once and returns a string is a function. What makes something agentic is the loop — it can decide it needs more information and go get it.

This matters for your project because it gives you a sharp test for whether a component deserves to be an agent at all, which your constitution states as PG-3: an agent is justified only where the task requires open-ended, tool-using interaction with an unbounded external world. Resolving whether a ticker was delisted or renamed qualifies — the answer is on the internet and you do not know in advance which query finds it. Computing portfolio concentration does not — it is a sum.

2.2 "Orchestrator" means three different things

This word is badly overloaded, and the ambiguity hides a real architectural decision. When someone says "the orchestrator", they may mean any of three things:

 What it isWho wrote itIntelligence
① The framework A library — LangGraph, CrewAI, AutoGen. Provides graph definition, state passing, checkpointing, retries. A vendor none Pure infrastructure. Knows nothing about investing.
② The orchestration component (D-08) ★ Your code. The graph topology, the routing functions, turn budgets, retry policy, run manifest. You deterministic Carries policy, not judgement. Plain functions.
③ An orchestrator agent An LLM that decides at runtime which agent to call next — the "supervisor" or "planner" pattern. A model non-deterministic Judgement in the control plane.

In Lecture 2, "orchestrator" always means ② — and ② is deterministic. Your L0 states it directly: D-08 "invokes; never computes." Every routing function in this lecture is a pure function you can exhaustively unit-test. LangGraph, if you adopt it, is ① — the library that ② is written in. They are not alternatives to each other; one implements the other.

Should the orchestrator carry intelligence? Almost certainly not — here

Option ③ is fashionable and is the default in a lot of tutorial content: let an LLM supervisor decide the plan. For an open-ended assistant that is reasonable. For your system it is the wrong trade, for three reasons.

It breaks auditability. "Why did this run use the 1-week model?" must have an answer. With ②, the answer is a recorded predicate: realised_vol_60d > 0.45. With ③, the answer is "the model felt it should", which is exactly the class of unfalsifiable output your constitution exists to prevent.

It violates AP-5. Routing on volatility is a definable computation. Handing a definable computation to an LLM is the capability-creep failure mode.

It makes replay meaningless. If control flow itself is stochastic, two runs on identical data can take different paths, and you lose the ability to attribute an outcome difference to anything.

★ Keep judgement in the agents, where it is bounded and its output is checkable. Keep the control plane deterministic. That division is the interesting architectural claim in your design, and it is defensible in a way "I used a supervisor agent" is not.

→ §2.8 treats option ③ properly: how you would build one, the non-LLM alternatives most discussions omit, where it genuinely belongs in industry, the four reasons it fails here, and what would have to change for that to reverse.

2.3 Orchestration frameworks: what they give you, and where they belong

Orchestration frameworks show up constantly in job descriptions, so it is worth knowing the landscape precisely rather than by reputation. First, a distinction that trips people up: there are two unrelated families of tool both called "orchestration".

  • Workflow / data orchestration — Airflow, Prefect, Dagster, Temporal. Schedule jobs, manage DAGs of tasks, retry, backfill. Temporal adds durable execution: a workflow survives process death and resumes. These are about reliability over long time horizons.
  • Agent orchestration — LangGraph, CrewAI, AutoGen, Semantic Kernel, LlamaIndex Workflows. Manage a graph of LLM-bearing steps with shared state, tool calls, and human interrupts. These are about control flow around non-deterministic components.

Your D-08 needs a little of both, and they are not competitors — a daily run could be scheduled by cron or Temporal and internally structured by LangGraph.

LangGraphExplicit state machine: StateGraph of nodes and edges, conditional edges, typed shared stateCheckpointing, time-travel replay, native human-in-the-loop interrupt(), streaming, topology you defineLangChain dependency surface; abstractions can obscure a clean domain layer
CrewAIRole-playing crew: agents with roles, goals, backstories; sequential or hierarchical processVery fast to a working demo; maps intuitively onto a "team"Topology is largely framework-chosen; conditional routing is hard to express; weaker introspection

What a framework actually buys you

Strip the marketing and there are five capabilities. Ask of each whether you would otherwise build it:

  1. Graph definition — nodes, edges, conditional transitions. You would write this anyway; it is ~200 lines.
  2. State management — a typed object threaded through nodes with merge semantics. Also modest.
  3. Checkpointing & replay — persist state after every node; resume or rewind. ★ This is the one with real depth, and it is exactly what F2 needs.
  4. Human-in-the-loop interrupts — pause the graph, surface to a person, resume with their input. ★ Maps directly onto your Seat 1.
  5. Streaming & observability — token and step streaming, tracing hooks. Useful for a demo.

Items 3 and 4 are the honest case for adopting one. Items 1, 2 and 5 you could write in a week.

The recommendation, stated with its trade-off

Use LangGraph, confine it to D-08, and be able to explain why. The explicit-state-machine model matches a system where you want to define the topology rather than have a framework infer it — and your topology is already fixed by the analyst firewall, which is a graph constraint (an absent edge). Checkpointing gives you F2's replay substrate. interrupt() gives you Seat 1 as a first-class node rather than a bolt-on.

The confinement rule matters more than the choice. LangGraph is imported by src/orchestration/graph/ and by nothing else — enforceable as a CI grep, exactly like ST-5 does for the LLM gateway. Agents stay plain Python classes behind AgentPort. If LangGraph is abandoned in 2028, you rewrite one directory.

★ And be honest about the weight. LangGraph is roughly a week to learn. It is a keyword on a CV, not an architecture. The defensible claim in an interview is not "I used LangGraph" — it is "I kept my domain logic independent of it, and here is the grep that proves it."

2.4 Part A — the control plane

Borrow the framing from networking. The data plane carries the payload: features, scores, theses. The control plane decides how the data plane is configured: which model, which horizon, which LLM tier, which prompt variant.

Configuration influence is a control-plane feature. Its implementation is unglamorous and that is the point:

# src/orchestration/graph/routing.py

def select_quant_variant(features: FeatureRow,
                         peer: FundamentalView | None) -> Routing:
    """Pure function. Same inputs → same variant, always.

    Note what it returns: a NAME and a REASON, not a model. Routing decides
    WHICH; the registry decides HOW to build it. Keeping those separate is
    what lets you unit-test routing without constructing a single model.
    """
    if features.realised_vol_60d > VOL_HIGH:
        return Routing(variant="horizon_1w",
                       reason="realised_vol_60d > 0.45",
                       influenced_by=None)

    if peer is not None and peer.thesis_horizon == "short":
        return Routing(variant="horizon_1w",
                       reason="fundamental thesis is short-horizon",
                       influenced_by="seat_2")   # ← PG-7: RECORD IT

    return Routing(variant="horizon_1m", reason="default", influenced_by=None)

Three properties make this good engineering rather than plumbing:

  • It is a pure function. You can exhaustively unit-test routing without instantiating a model, calling an LLM, or touching the network.
  • It returns a reason. When you later ask "why did this name get the one-week model?", the answer is in the trace, not in someone's memory.
  • It records influenced_by. This field is the whole subject of the next section.

Why influence must be mediated by the orchestrator

The tempting design is for the fundamental agent to call the quant agent directly. Resist it, for four reasons:

  • Coupling. Direct calls make n agents into n² potential dependencies.
  • Your import fence. ST-9 forbids src/fundamental/ and src/quant/ importing each other. Direct calls violate it structurally; mediation preserves it, because both agents import only the orchestrator's message types.
  • One place to enforce policy. Turn budgets, cycle detection and logging all need a chokepoint.
  • Replay. If influence flows through the orchestrator, the trace has every routing decision. If it flows peer-to-peer, reconstructing a run means reconstructing every agent's internal state.

What the orchestrator does not own: the decision

A natural question: does the orchestrator subsume D-12, the Decision domain? No — and keeping them apart is load-bearing. They answer different questions and fail in different ways.

 D-08 OrchestrationD-12 Decision
Question it answersWho runs, when, with what config?Given these views, what is the verdict?
Vocabularynodes, edges, retries, budgets, variantsBUY / HOLD / SELL, gates, conviction

The orchestrator routes a message to D-12 the same way it routes to any other node. It does not peek inside the payload and reason about whether BUY is warranted; it cannot, because it has no vocabulary for verdicts. D-12 in turn has no idea it was invoked by a graph — hand it the same views from a test harness and it returns the same verdict.

Why the separation is worth defending

The tempting shortcut, once you have a graph, is to put a little decision logic in a conditional edge: "if risk flagged concentration, route to HOLD." That single line has moved a verdict rule out of D-12 — where it is unit-tested, governed by the meet-semilattice, and provably unable to upgrade a verdict — into control flow, where none of those guarantees apply.

Do it three more times and your decision logic is scattered across routing predicates, PG-6's structural guarantee is void, and nobody can answer "what are all the ways this system can produce a BUY?" ★ A conditional edge may branch on which node runs next. It may never compute what the answer is.

One case makes the line vivid. During deliberation, two different "when do we stop" questions arise, and they belong on opposite sides:

  • "The turn budget is spent — stop arguing." → orchestrator. A protocol decision about control flow.
  • "The agents disagree; what is the combined verdict?" → D-12. A semantic decision about content.

The orchestrator ends the conversation. D-12 says what the conversation amounted to. If the orchestrator ever answers the second question, you have put judgement in the control plane by the back door — the same failure as option ③ in §2.2, arriving one conditional edge at a time.

Hazard 1: cycles

If A can reconfigure B and B can reconfigure A, you are computing a fixed point. Three ways to guarantee it halts, in descending order of how much I would trust them:

  1. Make the influence graph a DAG. Phase-order the agents; influence flows one way only. Termination is structural. Start here.
  2. Bound the iterations. Allow mutual influence but cap total rounds and define what happens at the cap — which must not be "use whatever we had."
  3. Prove monotonicity. Show each round moves a well-founded measure strictly downward. Elegant, and rarely true of anything involving an LLM.

Hazard 2 — the deep one: influence destroys independence

This is the part that is easy to get wrong and expensive to discover

Your architecture firewalls the fundamental and quantitative seats so their views are independent. The value of independence is statistical: when two independent estimators agree, that agreement is evidence. Informally, two independent looks at the same question, both landing on BUY, is meaningfully stronger than one.

Now condition B's configuration on A's output. B's view is no longer independent of A's given the data — you have introduced a path from A into B. Their agreement stops being evidence and becomes partly an echo. The system will still print "both seats agree", and that sentence will now mean something weaker than it did, with nothing on the screen to indicate the change.

The failure is silent, which is what makes it dangerous. Nothing crashes. A number that used to carry information quietly stops carrying it. This is exactly why PG-7 requires three things:

  1. Every cross-configuration request is recorded on the nomination (influenced_by).
  2. Decisions where one seat configured the other are bucketed separately in evaluation.
  3. The combined verdict may never claim "two independent views agree" when one configured the other.

Rule 2 is the one that turns this from a caveat into a measurement: you can compare the hit rate of influenced versus uninfluenced decisions and find out empirically what the influence cost you.

2.5 Part B — argumentation as a state machine

"Two agents argue" must become a protocol with typed messages and a guaranteed termination condition, or it becomes an unbounded chat that sometimes stops.

Model it as a finite state machine. Each message type is a transition, not a flavour of text.

Two design points that are easy to miss:

  • Messages carry structured payloads, not prose. A CHALLENGE should name the field it disputes and the value it expected. If the payload is a paragraph, the only thing that can consume it is another LLM, and you have lost the ability to branch on it deterministically.
  • Escalation is a first-class outcome. The alternative — forcing convergence — means the system silently averages a genuine disagreement, which is precisely the information you most wanted to see.

2.6 Why LLM debate often fails

This is the section to remember. Multi-agent debate is widely demonstrated and much less widely measured. There are three well-established reasons it can produce motion without information.

1 · Sycophancy

Language models tend to defer to pushback from a user or another model, adjusting their answer toward the challenger regardless of whether the challenge is correct. Anthropic's own work on the phenomenon (Sharma et al., 2023) found sycophantic behaviour across several production assistants, and it is a direct consequence of preference-based training: agreeable responses were rewarded.

In a debate protocol this is fatal. If the challenged agent revises whenever challenged, the "deliberation" measures who spoke last, not who was right.

The cheapest experiment in this entire lecture

Run your deliberation twice over the same set of decisions. Once with valid challenges from the risk agent, once with challenges that are deliberately wrong — cite a concentration figure that is false, an exposure that does not exist.

Then measure the capitulation rate in each arm. If the fundamental agent revises just as often against bogus challenges as against valid ones, your deliberation layer is transferring social pressure, not evidence — and you have discovered that with a few hundred lines and no new infrastructure.

Report that number either way. A measured capitulation rate is a stronger portfolio artifact than a transcript that looks impressive.

2 · Correlated errors

Ensembles gain from diverse errors. Two instances of the same base model, given the same context, share training data, biases and blind spots — their errors are highly correlated, so the second opinion adds far less than its cost implies. Worse, it can add confidence without adding accuracy: two agreeing agents feel like corroboration.

3 · Position and anchoring effects

Whichever agent speaks first frames the exchange; the second reacts to that frame rather than assessing independently. If you must have debate, randomise speaking order across runs and check whether outcomes depend on it. If they do, you are measuring the protocol, not the question.

When debate genuinely helps

The condition is asymmetry. Debate adds information when the participants are not interchangeable:

  • Asymmetric information — the risk agent can see the book; the fundamental agent cannot. The challenge carries facts the other side genuinely lacked.
  • Asymmetric tools — one can query filings, the other can run a simulation. The exchange moves real evidence.
  • Verifiable claims — the challenge cites a number that can be checked deterministically, so the revision is forced by arithmetic rather than by tone.

Note that all three describe your risk-versus-fundamental pairing well, and none of them describes two general-purpose LLMs discussing a thesis. That is the design brief: give the agents different information and different tools, and make every challenge cite something checkable.

2.7 Determinism, tracing, replay

You cannot debug what you cannot reproduce, and an LLM-bearing pipeline is not reproducible by default. Sources of non-determinism, in rough order of how much trouble they cause:

  • Sampling. temperature=0 reduces variance but does not guarantee identical output across model versions or backends.
  • Model version drift. A provider alias can move under you. Pin exact model identifiers and record them in the trace.
  • Tool results. A web search returns different results tomorrow. This is the big one for your corporate-action agent.
  • Concurrency. If agents run in parallel, message interleaving varies.

The practical resolution is not to chase bit-for-bit determinism. It is to record enough that a run can be replayed from its trace: every message, every tool call and its response, every routing decision with its reason, model ids, prompt versions, and a hash of the input snapshot. Replay then re-executes the graph against recorded tool responses instead of live ones.

This is why F2 (trace and replay) is a prerequisite for both halves of Feature 2, not a nice-to-have that follows them. Build the trace first; it is the substrate that makes everything else auditable — and it is the same substrate Lecture 3 needs.

2.8 The road not taken: the AI orchestrator agent

§2.2 introduced option ③ — an orchestrator whose control decisions are made by a model rather than by a program — and set it aside in three sentences. It deserves more, because it is the default in a great deal of current writing, because it is genuinely right for some systems, and because knowing precisely why it is wrong here is more valuable than not having considered it.

Definition

What makes an orchestrator "AI-powered"

An orchestrator is AI-powered when the policy — the function mapping current state to next action — is learned or inferred rather than written. The distinction is not whether the system contains a model; your deterministic orchestrator invokes models constantly. It is whether a model decides what happens next.

Every such orchestrator, regardless of technique, has the same five parts. Designing one means making five decisions:

  1. State representation — what the policy can see. The most consequential choice. A raw transcript is easy and unbounded; a typed state object is disciplined and requires you to know in advance what matters.
  2. Action space — the set of legal next moves, which must be enumerable and validated. Naive implementations let the policy emit free text and hope it names a real tool. Every proposed action must be checked against the registry before execution.
  3. Policy — state → action. This is the "AI" part, and it has more implementations than people assume (below).
  4. Termination — a halting guarantee. Step budget, cost budget, or a proven terminal condition. Never "the model decides it is done", alone.
  5. Guardrails — validation, budget enforcement, and a deterministic fallback for when the policy proposes something illegal or the budget expires.

For LLM policies specifically, the recurring architectures are ReAct (Yao et al., 2022 — interleaved reasoning and action), Plan-and-Execute (plan up front, then run — cheaper, less adaptive), supervisor/hierarchical (a router delegates to workers and collects results), Reflexion (Shinn et al., 2023 — self-critique between attempts), and Tree of Thoughts (Yao et al., 2023 — search over reasoning paths).

Explainable AI: Attribution, Evidence, and Calibrated Doubt

Why a convincing explanation and a true one are different objects — and what to build when the thing you must explain is a recommendation someone will trade on.

Your system produces a ranked list and a thesis. A portfolio manager who must own the P&L cannot act on either without knowing why. This lecture is about producing that "why" in a form that is actually true.

The whole lecture in six claims

1 · A convincing explanation and a true one are different objects. An explanation that is plausible but does not describe the actual computation is worse than none, because it manufactures confidence. Everything below follows from taking this seriously.

2 · You have two things to explain and they need opposite techniques. The ML ranker is numeric and can be attributed to its inputs. The LLM thesis cannot be introspected at all. Treating them with one method fails on both.

3 · For the ranker — attribute, but first ask whether you need to. SHAP is the principled default. The stronger move, for a high-stakes decision with a marginal signal, may be to use a model that is interpretable by construction and skip post-hoc explanation entirely.

4 · For the LLM — do not ask it why. Self-reported reasoning is demonstrably unfaithful. Replace introspection with verification: bind every factual claim to a source span and check it deterministically.

5 · An explanation without calibration is half a product. "Why" is useless without "how much should I trust this", and confidence that nobody has measured against outcomes is decoration.

6 · Explanations are outputs, so they get tested. Faithfulness, stability, and whether they actually changed a decision correctly. Untested explanations drift toward whatever is most persuasive.

Sections 3.1–3.2 establish claims 1 and 2; 3.3–3.5 work through the techniques for each half; 3.6–3.7 cover calibration and testing. If you read one section, read 3.4.

3.1 The distinction everything else depends on

Faithfulness vs plausibility

Plausible: the explanation is coherent, readable, and satisfying to a human.
Faithful: the explanation accurately describes the computation the system actually performed.

These are independent. An explanation can be highly plausible and completely unfaithful, and that combination is worse than no explanation at all — because it manufactures confidence while conveying nothing about the mechanism. A system optimised only for explanations users like will drift toward exactly this failure.

Keep a second distinction alongside it. Explanation answers "what did the model do?" Justification answers "is this a good decision?" Attribution methods answer the first. They are silent on the second, and treating them as if they answered it is a category error you will see constantly in practice.

Standard taxonomy, briefly:

  • Intrinsic (a linear model, a shallow tree, a GAM — the model is the explanation) vs post-hoc (explain a black box after the fact).
  • Global (how does the model behave overall?) vs local (why this prediction?).
  • Model-specific (TreeSHAP) vs model-agnostic (LIME, permutation).

Your recommendation surface needs local explanations. "Momentum matters in general" does not help someone decide about one name today.

3.2 Attribution for the ranker

Built-in importance — global, and misleading

Gradient-boosted trees expose gain or split_count importance. Both are global, and both are biased toward high-cardinality continuous features simply because such features offer more places to split. Useful for a rough sanity check; not an explanation of any individual prediction.

Permutation importance — and its correlated-feature trap

Shuffle one feature's column, measure how much performance drops. Intuitive and model-agnostic. Two serious caveats:

  • Correlated features hide each other. If momentum_60d and momentum_90d are 0.95 correlated, permuting either alone barely hurts — the model leans on the survivor. Both look unimportant; together they may be the entire signal.
  • It evaluates off-manifold. Shuffling creates rows that could not exist (a micro-cap's volume on a mega-cap's spread), so you are measuring model behaviour in a region it was never trained on.

SHAP — additive attribution with axioms behind it

SHAP (Lundberg & Lee, 2017) applies Shapley values from cooperative game theory (Shapley, 1953) to feature attribution. The prediction is the "payout"; features are "players"; a feature's attribution is its average marginal contribution across all orderings in which players join the coalition.

What you buy with that machinery is three properties:

  • Local accuracy (efficiency) — attributions sum exactly to the prediction minus a baseline. Nothing unexplained, nothing double-counted.
  • Missingness — a feature absent from the model gets zero attribution.
  • Consistency — if a model changes so a feature contributes more, its attribution cannot go down. Gain importance violates this; that is the concrete reason to prefer SHAP.

Exact Shapley values are exponential in the number of features. TreeSHAP computes them in polynomial time for tree ensembles, which is why SHAP is practical for your LightGBM ranker specifically.

Three things SHAP does not give you

It is not causal. SHAP explains the model's dependence on inputs, not the world's. "Margin drove the score" does not mean margin drives returns.

Correlation still bites. Interventional and conditional (observational) SHAP disagree under correlated features, and they answer different questions. Know which one your library computes and why you wanted that one.

Explaining a wrong model faithfully is still wrong. With walk-forward IC at 0.0203 and t = 1.42, an explanation of your current ranker is a faithful account of a signal not yet distinguishable from noise. Say so on the page. An explanation attached to an unpromoted model must carry that status, or it lends borrowed authority.

The ranking subtlety

Here is a wrinkle specific to your system that generic tutorials will not cover. Your model produces a ranking over a cross-section, and your decision uses the rank. But SHAP explains the pointwise score. These are different questions:

  • "Why is AAPL's score 0.71?" — pointwise. SHAP answers this directly.
  • "Why is AAPL ranked 3rd?" — relational. It depends on the other 497 names that day. AAPL's rank can change with its own score unchanged.

Answer both, separately and honestly: report the score attribution, then explain the rank via the cross-sectional score distribution on that date ("0.71 sits at the 99th percentile of today's cross-section; the 90th percentile is 0.55"). Presenting a score attribution as if it explained the rank is a small dishonesty that will eventually mislead someone — most likely you, in six months.

Attribution stability as a diagnostic

Re-run attributions under small input perturbations, different seeds, or adjacent dates. If the top drivers churn wildly while the prediction barely moves, the explanation is describing noise rather than a stable property of the model.

Treat that as a finding about the model, not a display bug — it is evidence that the model's decision surface is unstable in that region. This is one of the highest-value diagnostics available to you and almost nobody computes it.

3.4 Explaining the LLM half — do not ask it

Chain-of-thought is not an account of the computation

Turpin et al. (2023), Language Models Don't Always Say What They Think, showed that models' stated reasoning can be systematically unfaithful: introduce a biasing feature into the prompt — for instance, reordering multiple-choice options so the answer is always (A) — and models' answers shift toward the bias while their chain-of-thought never mentions it, instead constructing plausible support for the biased answer.

So a self-reported rationale is not evidence about why the model produced its output. It is another generated artifact, subject to the same failure modes as the output.

This has a sharp architectural consequence. Since you cannot obtain a faithful explanation of an LLM's internal process by asking, stop trying to explain the reasoning and instead constrain and verify the claims.

That is what evidence binding does, and it is the design your project already specifies as RA-6 and RA-9:

# The check is DETERMINISTIC. This is the entire point.
# Verifying an LLM's output with a second LLM call inherits the first
# model's blind spots and gives you a correlated judge, not a check.

def verify(claim: Claim, span: EvidenceSpan) -> VerificationResult:
    """RA-6 — a claimed value must be PRESENT IN, or ARITHMETICALLY
    DERIVABLE FROM, the cited span. No model is consulted."""
    if claim.value in parse_numerics(span.text):
        return VerificationResult.VERIFIED
    if derivable(claim.value, parse_numerics(span.text), claim.operation):
        return VerificationResult.DERIVED
    return VerificationResult.UNVERIFIED      # → the thesis fails loud (P5)

Your as-built register records that half of this runs and half does not: extraction is checked against its source, but Thesis.claims is empty on every authored thesis, so the judgement narrative is unverified (AB-2). If the model writes "NAND margins expanded on HBM demand", nothing currently checks it against the filing.

That gap is the single highest-value item in your explainability lane, for a reason worth stating plainly: a reader who sees a thesis pass every test will reasonably conclude its prose was verified. Today only its falsifiers were. Closing AB-2 converts a plausible narrative into a checked one.

Metrics that follow naturally, and that you should track as gates rather than dashboards: grounding rate (fraction of factual claims bound to a verified span), unbound-claim count (must be zero for an actionable report), and span precision (does the cited span actually contain the claim, sampled and human-checked).

3.5 Counterfactual explanation

Formally (Wachter et al., 2017): given input x with outcome f(x), find x′ minimising a distance d(x, x′) subject to f(x′) equalling some desired outcome. In words: the smallest change that would flip the answer.

For a decision-support system this is often more useful than attribution, because it is actionable. "Margin contributed −0.08 to the score" is a fact about the model. "This becomes a BUY if gross margin holds above 42% for two more quarters" is something a portfolio manager can monitor, and it doubles as a falsification condition.

Four desiderata, and they trade off against each other:

  • Validity — the counterfactual really does flip the model's output.
  • Proximity — it is close to the actual input. A counterfactual requiring ten simultaneous changes explains nothing.
  • Sparsity — few features change. Humans reason well about one or two moving parts.
  • Plausibility / actionability — it stays on the data manifold and changes only things that can change. "If this company were founded in 1990" is not an explanation.
Express counterfactuals in observables, never in features

f_gross_margin_z increasing by 0.4σ is uninterpretable and unmonitorable. "Gross margin holds above 42% for two more quarters" is both. The counterfactual search happens in feature space; the presentation must be translated back into the observable quantities the manager can actually watch — which means your feature contract needs an inverse mapping to named, human-scale quantities.

Same wrinkle as before: for a rank, a counterfactual is conditional on the peer set. Entering the top decile requires passing other names, so state it as of a date and universe, not as an absolute.

3.6 Calibration — the honest confidence

An explanation says why. Calibration says how much to trust it. A model is calibrated when, among all predictions made with confidence p, the outcome occurs about a p fraction of the time. Confidence of 0.8 should be right 80% of the time — no more, no less.

Modern high-capacity models are typically overconfident — Guo et al. (2017) documented this systematically for neural networks, and the same tendency shows up in LLM verbalised confidence.

Two measures worth knowing:

  • ECE — Expected Calibration Error. Bin predictions, take the weighted mean absolute gap between confidence and accuracy. Simple and readable; sensitive to binning choices.
  • Brier score — mean squared error of the probabilistic forecast. It decomposes into reliability (calibration), resolution (how much predictions vary usefully) and uncertainty (irreducible). The decomposition is the useful part: it separates "your probabilities are miscalibrated" from "your probabilities are all 0.5 and say nothing."
Coverage is not calibration — and your register conflates them

AB-1 defines confidence := evidence_coverage: the fraction of rubric items that found real evidence. That is a genuinely good measure of how much the system looked at. It is not a measure of how often the system is right.

A thesis can have 100% evidence coverage and be wrong; it can have 60% coverage and be right. You need both numbers, and they should not share a field name. Coverage is an input-completeness metric available immediately; calibration is an outcome metric that requires waiting for resolution.

The current state is at least honest: the field reads {"value": null, "basis": "not_measured"} rather than a fabricated zero. Keep that property when you wire coverage in — and note the trap already recorded: once coverage becomes a real number, the CONFIDENCE_FLOOR at 0.3 becomes reachable and will start forcing INSUFFICIENT_DATA. That will look like a regression on the first run that hits it. It is the mechanism working.

3.7 How to evaluate an explanation

Explanations are outputs, so they need tests. Three families:

  • Faithfulness — deletion / insertion curves. Remove the top-k attributed features and measure how fast performance degrades; then add them back to an empty input. A faithful attribution degrades the model fast on deletion and recovers fast on insertion. If removing the "most important" features changes nothing, the attribution is not describing the model.
  • Stability. Perturb inputs slightly; attributions should move slightly. Quantify it rather than eyeballing it.
  • Human utility. The one that actually matters and the one most often skipped: does the explanation change a decision, correctly? You are the user here, which makes this cheap to run — log the cases where an explanation changed your action, and revisit them at resolution.

All three belong in the evaluation harness (F5), not in the explanation module. An explanation module that grades its own explanations is the same structural mistake as an LLM judging its own output.

3.8 Why this is worth eight months of anyone's attention

Two reasons beyond the engineering.

It is the harder skill. Orchestration frameworks are learnable in a week and the supply of people who have done a tutorial is large. Building a system that can say why, and prove the why is faithful, requires understanding the model, the statistics and the failure modes — and far fewer people have done it.

Finance is where it is mandatory. Model risk management practice (the Federal Reserve's SR 11-7 guidance is the canonical reference) requires that models used for material decisions be documented, validated and explainable. The EU AI Act pushes in the same direction for high-risk applications, and credit and investment decisions sit squarely in scope. "I built explainability into a financial recommendation system, and measured its faithfulness" maps onto real, funded job descriptions in a way that "I built a multi-agent demo" does not.
